# R31.1 — an interface states its protocol

**Status:** open
**Drafted:** 2026-10-06. Surface and domain decided below; the emission target has
one open choice that needs a tool check before it can close.
**Relates to:** [`hdl-spec.md`](../../hdl-spec.md) R31 (interface), R8 (handshake),
R27 (simulation-only), R4.1 (a declaration's domain region), R13.1 (a port is
declared before the clock domain exists). The protocol half comes from a design
note outside this repository, *a contract is checked where it is bound*.

> That design note is provenance only and is not reachable from this
> repository.

---

## The question this answers

R31 writes an interface's **directions** once, from the master's side, and every
endpoint gets them. It writes nothing about how the leaves may change. So a
protocol's rules live in prose — `MemAccess`'s are three sentences in a comment —
and every endpoint that binds the interface is trusted to have read them.

```
                    what R31 states        what is missing
Interface.body      per-leaf direction     how the leaves may change over time
                    (valid out, ready in)  (payload stable while valid holds)
```

The four defects that opened the sibling document are all of the second kind: a
value that was wired correctly and *behaved* wrongly. The document's own set of
four properties is the worked example:

1. `valid` is not retracted before `ready`;
2. the payload is stable while `valid` stands;
3. a response arrives only while a request is outstanding;
4. at most one response per request.

(1)–(2) are the master's side of a handshake; (3)–(4) belong to a
request/response pair such as `MemClient`. Each is a claim about **two adjacent
clock edges**, so each needs history — which is the whole of the difficulty.

## Decision 1 — where the protocol is written: in the interface body

An interface states its protocol beside its fields, as expressions over the
fields' own `val`s.

```scala
final class Handshake[P, H](p: => P)(using Blueprint[P, H]) extends Interface:
  val valid   = Out(Bool())
  val ready   = In(Bool())
  val payload = Out(p)

  protocol {                                   // the same body, one more fact
    assert(valid & ~ready |=> valid, "valid retracted before ready")
    assert(valid |=> stable(payload), "payload changed while valid")
  }
```

Why here and not at the endpoint:

- **The properties must name the fields.** `valid`, `ready` and `payload` are
  real `val`s in the body (R1/R31), so a property written there refers to them as
  the same symbols a reader does. A protocol declared anywhere else would have to
  name its leaves by string, which is the thing R1 exists to avoid.
- **One place, every endpoint.** This is R31's own bargain applied to the second
  fact: written once in the definition, emitted at each binding. `Handshake`
  carries its two; a user interface (`MemClient`) carries its own.
- **The endpoint's role is not the protocol's business.** A property is written
  from the master's side, exactly as the directions are, and the role reverses
  the offsets at emission. The alternative — two properties, one per side — is
  the repetition R31 removed.

Rejected: **a named protocol object bound at the endpoint**. It reads as
configuration rather than declaration, it lets two endpoints of one interface
carry different protocols (so the shape is no longer one fact), and it puts the
protocol where the fields are not.

## Decision 2 — which clock it is checked on: the endpoint's domain, at freeze

A port is declared before the module's clock domain exists (R13.1), so the
protocol cannot be attached when it is written. It attaches when the module
freezes:

```
Interface.bind (port-time)        Builder.freeze (module-time)
────────────────────────          ────────────────────────────
one port per leaf, named          for each bound endpoint:
<base>_<field>                      domain := region around the
                                    declaration (R4.1) else the
                                    module's own domain
                                    → add the protocol's checks to
                                      that domain's check block (R27)
```

- **The region wins.** R4.1 already lets a declaration sit in a region that names
  its domain (`domain(clk) { … }`); an endpoint declared there is checked on that
  clock. In its absence, the module's own domain is the only clock it could have.
- **The reset guard is the domain's** (R13), which is what a concurrent assertion
  spells `disable iff (reset)` and what R27's check block already emits.
- **A module that names no clock emits nothing.** An endpoint whose domain is
  `noClock` — an `AddrDecoder` whose whole body is combinational — has no edge to
  sample. The protocol is not checked there, rather than checked wrongly. This is
  a boundary to state, not a case to hide.

## Decision 3 — the emission target: open

Two forms are on the table and they differ by more than syntax.

```
                    history               can state an assume?   checked by
R27 immediate       needs a shadow        no — assert only       any simulator
check (today)       register you add
SVA in a sidecar    free — |=>, $stable   yes — assume property  Verilator --assert,
                                                                 possibly formal
```

- **R27 immediate checks.** The spec's current position: R27 is where such a check
  would be emitted, `scalahdl.lib.Skid` states its own invariant that way, and
  the block is deleted under `// synthesis translate_off`. But properties (1)–(3)
  compare against the previous edge, and R27 forbids declaring or assigning
  anything inside `simOnly` — so a shadow register would have to live inside the
  `translate_off` region, which stretches the construct's bit-identity promise.
- **SystemVerilog concurrent assertions in a sidecar `.sv`.** `valid |=> valid`
  and `$stable(payload)` are the properties directly, with no history register; a
  protocol's environment side can be `assume`d, which R27's `check` cannot do;
  and the Verilog-2001 output is untouched, so R09's promise is kept. It is a new
  emission artifact beside R09's two design languages, and it is exactly what the
  spec reserved at [`hdl-spec.md:3136`](../../hdl-spec.md) — *"Concurrent
  assertions (`assert property`) carry a clocking block of their own and belong
  to their own rule if they are ever wanted."*

**The check that decides it:** whether the tools in use honour it. Verilator
checks `assert property` under `--assert`; whether the installed version handles
`bind`, and how it treats `assume` (many simulators ignore it), must be measured
on a throwaway file before the target is chosen. Until then the spec commits to
R27's immediate checks and names the sidecar as future work.

## The surface

Minimal and precise:

- a property is `assert(<boolean over the fields>, "message")`, plus an
  `assume(...)` for the environment's side if the sidecar is chosen;
- two temporal helpers cover all four: `next(x)` (SVA `|=>`) and
  `stable(x)` (SVA `$stable`);
- the protocol block is compiled the same way a driver block is, so R6.1 literal
  resolution, R11 completeness and the R27 "drives nothing" rule all apply
  unchanged;
- a property may only read the interface's own fields and the module's signals;
  it may never drive, which is R27's rule stated once more.

## What the spec now says — R31.1

Written into `hdl-spec.md` §5 after R31, and R8's *Future* note repointed at it:

> An interface may state its **protocol** beside its fields. The statements are
> expressions over the fields' handles, and every endpoint that binds the
> interface emits them as simulation-only checks (R27), in that endpoint's own
> clock domain, guarded by the domain's reset. … A handshake is the worked
> example, four properties: `valid` is not retracted before `ready`; the payload
> is stable while `valid` stands; a response arrives only while a request is
> outstanding; at most one response per request.

with the three bullets that decide the clock, the no-clock boundary, and the
removability of the checks.

## What this does not do

- **Not a general assertion language.** The four properties are one-clock
  statements; the only temporals are `next` and `stable`. A property language
  with arbitrary sequences is not asked for and is not this.
- **Not the switch-completeness half.** That finding was not a protocol violation: a
  `switch` over a named encoding grew a member and an arm written for the rest
  kept it. That is `Region` saying which members a store answers for, and,
  generally, R24's completeness rule — a separate item, deliberately left out
  here.
- **No hardware.** The checks are the design's reading of its own protocol, and a
  design with them is bit-identical to one without.

## Owed

- **R31 and R8**: pointers to R31.1; R8's *Future* note replaced.
- **Roadmap**: a milestone or a follow-up under R31/R8, since R31.1 is a new
  requirement and not a sub-task of a closed one.
